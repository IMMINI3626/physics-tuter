# 서버 구현 결정 기록 (Cloud Functions)

`functions/index.js`·`functions/prompts.js`의 구현 결정과 그 근거를 모아둔다.

이 문서를 만든 이유는 근거를 코드 주석에 길게 쓰다 보니 파일이 1341줄까지 늘어났고, 로직을
읽으려면 근거 문단을 계속 넘겨야 했기 때문이다. 근거는 여기에 남기고 코드에는 한 줄 요약과
이 문서의 절 번호만 둔다. 측정 이론(BKT·레벨·승급)은 [오개념측정_BKT_설계.md](오개념측정_BKT_설계.md)에 있다.

---

## S-1. 호출 자격 검사 (`authorize`)

**발견한 문제.** 배포된 Functions 5개가 모두 `request.auth`를 보지 않았다. 함수 URL은 배포된
프론트 번들에 그대로 들어 있으므로, 주소만 알면 누구나 Gemini 호출을 대신 시킬 수 있었고
요금은 이 프로젝트에 청구됐다. 저장소 안의 `functions/test_api.js`가 `Authorization` 헤더
없이 실제 응답을 받아오는 것이 그 증거였다(지금 그 스크립트는 토큰 없이는 동작하지 않는다).

**익명 로그인을 통과시키는 이유.** 비로그인 무료 체험을 없애지 않기로 했다. 익명 사용자도
`uid`는 있으므로 서버가 호출 수를 셀 수 있다.

**그래서 일일 상한이 필요하다.** 익명 토큰은 누구나 무한정 발급받을 수 있어서 자격 검사만으로는
남용을 못 막는다. `uid` 단위로 하루 호출 수를 센다.

| | 상한 | 환산 |
|---|---|---|
| 익명(게스트) | 40회 | 약 15세트 |
| 로그인 | 400회 | 약 150세트 |

한 세트에 드는 호출은 생성 1 + 채점 1 = 2회다. Level 3은 풀이 인식·풀이 채점이 붙어 3~4회.

**카운터는 트랜잭션으로 센다.** 동시 호출에서 증가분이 씹히면 상한이 무의미해진다.
날짜 경계는 KST — UTC로 하면 오전 9시에 초기화돼 사용자가 체감하는 "오늘"과 어긋난다.

**⚠️ `authorize`는 반드시 각 함수의 `try` 블록 *밖에서* 부른다.** 안에서 부르면 그 함수의
`catch`가 `unauthenticated`/`resource-exhausted`를 `internal`로 덮어쓴다. 그러면 클라이언트가
"다시 시도하면 되는 오류"와 "다시 해도 막히는 오류"를 구분할 수 없다. 이 규칙은 코드에도
남겨뒀다.

**미룬 것.** App Check(reCAPTCHA v3). 콘솔 설정이 필요해 별도 작업으로 뒀다. 지금은 익명
토큰이라도 발급받아야 호출이 되는 상태다.

## S-2. 오개념 마스터 캐시 (`loadMisconceptions`)

오개념 128건은 `seed.js`로만 바뀌는 정적 데이터인데, 예전에는 `extractKeywords`가 호출마다
컬렉션 전체를 다시 읽고 `generateQuestions`가 또 소단원 쿼리를 따로 냈다. 사진 한 장에 128건
읽기가 그대로 붙는다. 프롬프트에 실어 보낼 목록이라 매번 최신일 필요도 없다.

인스턴스가 살아있는 동안 모듈 스코프에 들고 있는다.

**트레이드오프.** 시딩을 다시 했다면 인스턴스가 교체될 때까지(보통 수 분) 옛 목록이 쓰일 수
있다. 문제 생성은 이 목록에서 "고르는" 작업이라 그 지연은 감당 가능하다. 즉시 반영이 필요하면
함수를 재배포한다.

## S-3. 참고 문장 조회 (`in` 청크)

예전엔 오개념 id마다 쿼리를 하나씩 날려서 소단원 하나에 최대 22번이 됐다(뉴턴 운동 법칙 22개).
Firestore `in` 연산자가 한 번에 30개를 받으므로, 30개씩 묶으면 지금 데이터에서는 어느
소단원이든 쿼리 1회로 끝난다. 청크 로직을 남겨둔 것은 오개념이 30개를 넘는 소단원이 생겼을 때를
위한 것이다.

## S-4. 모델 파라미터 (`getGeminiModel`)

`gemini-2.5-flash`는 추론(thinking)이 기본으로 켜져 있고 그 양이 적응적으로 늘어난다.
thinking 토큰은 **출력 토큰으로 과금되고 응답 지연의 최대 요인**이다. 그래서 작업별로 예산을
따로 준다.

| 작업 | thinkingBudget | 이유 |
|---|---|---|
| 이미지 분류(`extractKeywords`) | 0 | 정해진 목록에서 고르는 분류 |
| 손글씨 OCR(`recognizeSolutionImage`) | 0 | 옮겨 적기만 함 |
| 문항 검수(`verifyStatements`) | 256 | 문장 하나씩 참·거짓 판정 |
| 문장 5개 생성 | 512 | 개념 참·거짓이라 추론 부담이 작음 |
| 서술형 채점(`gradeAnswers`) | 512 | 루브릭 적용 + 해설 |
| L2 방식B 계산 생성 | 1024 | 정답 숫자가 맞아야 함 |
| 풀이 과정 채점 | 1024 | 다단계 논리 타당성 평가 |
| L3 복합 계산 생성 | 2048 | 두 법칙 결합 계산의 논리 일관성 |

**`maxOutputTokens` 함정.** 2.5 모델에서 thinking 토큰과 실제 답변 토큰은 `maxOutputTokens`
예산을 **함께** 쓴다. 그래서 이 값을 답변 크기에만 맞춰 잡으면 추론이 예산을 다 써버려 답변
JSON이 중간에 잘려 나온다(파싱 실패). `getGeminiModel`은 `outputTokens`를 "답변에 필요한
양"으로 받고 내부에서 `maxOutputTokens = thinkingBudget + outputTokens`로 설정한다.

**SDK 주의.** `@google/generative-ai@0.21`의 타입 정의에는 `thinkingConfig`가 없지만,
`generationConfig` 객체를 필드 필터링 없이 v1beta API로 실어 보내므로 2.5 모델에서 정상
적용된다. (이 패키지는 deprecated — `@google/genai`로 옮기는 것은 별도 작업)

**함수 타임아웃 120초.** 예산 제한으로 호출당 지연이 크게 줄어, 재시도 3회를 감안해도 충분하다.
이 값은 비용이 아니라 최악의 대기시간 상한이다 — 낮을수록 사용자가 무한정 기다리는 일이 없다.

## S-5. 재시도 (`withRetry`)

LLM은 특성상 일정 비율로 형식을 어긴다 — 응답이 중간에 잘려 JSON 파싱이 깨지거나, 문장 5개를
요청했는데 4개를 주는 식이다. 예전에는 이런 경우 곧바로 `HttpsError`를 던져서 사용자에게
"다시 시도해주세요" 토스트가 그대로 노출됐다. 주문을 잘못 알아들은 직원에게 다시 물어보지도
않고 손님한테 안 된다고 하는 셈이라, 서버에서 조용히 두 번 더 시도한다(최초 1회 + 재시도 2회,
400ms → 800ms 대기).

**⚠️ 검증(파싱·형식 확인)까지 `fn` 안에서 해야 의미가 있다.** 검증을 밖에서 하면 "형식이 틀린
응답"이 재시도를 유발하지 못하고 그대로 실패로 빠진다.

**마지막 시도의 원칙.** 재시도를 다 쓴 뒤에는 항목에 따라 다르게 처리한다.

| 어긋난 것 | 마지막 시도 처리 | 근거 |
|---|---|---|
| 문장 수 ≠ 5, 힌트 누락, 틀린 문장 0개 | 실패 | 채점이 성립하지 않는다 |
| 틀린 문장 개수 ≠ 요청 | 통과 + 경고 로그 | 1개 이상이면 채점은 된다 |
| Level 1에 계산 문장 | 통과 + 경고 로그 | 라벨이 아니라 난이도 문제다 |
| 참·거짓 라벨 불일치 | 검수 라벨 채택 | 판정 전용 호출이 더 믿을 만하다 |

공통 기준은 "학생에게 *문제 생성 실패*를 띄우는 것이 더 나쁜가"다.

## S-6. 계산형 문항 검증 (`validateCalcQuestion`)

**`unitOptions`에 정답 단위가 실제로 들어있는지 확인하는 것이 핵심이다.** 프론트
(`QuizScreen.initCalc`)는 보기를 셔플한 뒤 `선택값 === calcQuestion.unit`으로 채점한다.
보기 안에 정답 단위가 없으면 학생이 무엇을 고르든 **무조건 오답**이 된다.

**표기만 다른 경우는 재시도하지 않고 교정한다.** 정답 `m/s²`인데 보기가 `m/s^2`이면 그 자리를
정답 문자열로 맞춰준다(`normalizeUnit`이 위첨자·`^`·공백·중점·대소문자를 무시하고 비교).
이런 사소한 차이로 3번씩 재생성하면 비용·지연 낭비가 크다. 실질이 다른 단위가 없을 때만 실패시킨다.

`solutionSteps`는 Level 3에서만 요구한다 — "다시 풀기"로 문제를 복원할 때 모범 풀이 단계가
필요하기 때문이다. 이 분기가 `label === 'L3'` 문자열 비교로 되어 있어, 라벨을 바꾸면 검증이
조용히 약해진다.

## S-8. 문항 검수를 별도 호출로 두는 이유 (`verifyStatements`)

문장을 만드는 호출은 오개념 겨냥, 개수 맞추기, 소재 다양화, 공식 문장 혼합을 동시에 처리한다.
검수 호출은 **문장만 보고 판정한다.**

**문장 외의 맥락을 일부러 주지 않는다** — 오개념 목록, 겨냥 지시, 생성 라벨, 학생 답변을 주면
생성 호출의 판단을 그대로 따라가 검수가 성립하지 않는다.

판정 항목은 두 개다.

- `isFalse` — 참·거짓 라벨이 맞는가. 생성 호출이 `isWrong`을 반대로 다는 사고가 실제로 났다.
- `needsCalc` — 수를 대입해 계산해야 판별되는 문장인가. Level 1 계산 문장 누출을 막는다(단계 8-6).

검수 호출이 실패하면 생성을 막지 않고 검수를 생략한다(`null` 반환). 품질 장치이지 필수 경로가
아니다.

자세한 판정 기준과 도입 경위는 설계 문서 [단계 8-5 / 8-6 / 8-7](오개념측정_BKT_설계.md)에 있다.

## S-9. 파일 구조 (2026-07 정리)

정리 전 `functions/index.js`는 1341줄이었고 그중 `generateQuestions` 한 함수가 518줄
(파일의 39%)이었다. 그 안에 생성기 3개(L3 계산 / L2 방식B 계산 / 문장 5개)와 프롬프트 템플릿
4개가 함께 들어 있었다.

**측정한 중복.**

- `[필수 규칙 - 어투 및 표기]`의 유니코드 기호 6줄이 세 프롬프트에 **바이트 단위로 동일하게** 복사
- L3와 L2 방식B의 `withRetry` 블록 15줄이 라벨·`isLevel3`·프롬프트만 빼고 동일
- 내용이 없는 빈 섹션 헤더(`보조 오개념 마스터 ...`)가 남아 있었음

**바꾼 구조.**

| 파일 | 역할 |
|---|---|
| `functions/prompts.js` | 프롬프트 템플릿 8종 + 조건부 블록. 전부 문자열을 돌려주는 순수 함수 |
| `functions/index.js` | `onCall` 5개 + 공용 헬퍼 + 후처리 로직 |

`generateQuestions`는 다음으로 쪼갰다.

- `loadUnitContext` — Firestore 3개 컬렉션 + 랜덤 요소를 모아 프롬프트 재료를 만든다
- `validateStatementSet` — 문장 5개의 형태·개수·힌트 검증
- `normalizeTags` — 오개념 태그 정리(영역이 같을 때만 2개 유지)
- `reviewStatementSet` — 검수 호출 + 계산 문장·라벨 대조

**⚠️ `loadUnitContext`의 `Math.random()` 호출 순서**(패턴 셔플 → `wrongCount` → 출제 관점 →
시드)는 바꾸면 안 된다. 같은 입력에 같은 프롬프트가 나오는지 검증할 때 이 순서가 기준이 된다.

**검증 방법.** 테스트 코드가 없어서, SDK와 `firebase-admin`을 가짜로 바꿔치기해 Gemini에
실제로 보내는 프롬프트 문자열을 8개 경로에서 캡처하고 리팩터링 전후를 바이트 비교했다
(`generationConfig` 포함, md5 동일). 후처리 로직은 AI 응답을 시나리오별로 주입해 8가지
경우(태그 병합·영역 불일치·개수 불일치·라벨 뒤집기·계산 문장 누출·문장 수 부족·L3·L2B)를 확인했다.
프롬프트를 옮길 때 문구는 한 글자도 바꾸지 않았다 — 문구가 바뀌면 AI 출력이 바뀐다.

## S-10. 미답변 문항에는 가점하지 않는다 (`scoreFeedbackItems`)

**증상.** 학생이 답을 쓰지 않은 문항에 AI가 점수를 주면 그 점수가 총점에 그대로 들어갔다.
아무것도 쓰지 않았는데 최종 100점이 나오면서 부제는 "틀린 문장 1개 중 0개 정답"으로 뜨는,
**점수와 판정이 서로 모순된 결과**가 가능했다.

**원인.** 바로 윗줄에서 `isCorrectAnswer`는 미답변을 명시적으로 걸러낸다.

```js
if (!answered)     isCorrectAnswer = !isWrong;   // 안 고름 → 틀린 문장이면 못 찾은 것
```

그런데 점수 분기는 `answered`를 보지 않고 AI가 준 값을 그대로 더했다.

```js
} else if (isWrong) {
  rawScore += (gradedItem?.score || 0);
```

프롬프트(`P.gradeAnswers`)에 "0점: 답변을 아예 작성하지 않은 경우", "score: … (미답변이면 0)"
규칙이 있어 정상적으로는 0이 온다. 하지만 **그 방어선은 AI의 준수 하나뿐**이었고, 어기면
막을 것이 없었다. 판정은 서버가 확정하면서 점수만 AI를 믿은 것이 어긋난 지점이다.

**고친 것.** 점수 가산에 `answered` 조건을 붙였다(`else if (isWrong && answered)`). 미답변인데
점수가 붙어 온 경우는 버리고 `console.warn`으로 건수를 남긴다.

**왜 다른 곳은 안 건드려도 되는가.** 이 수정이 바꾸는 값은 `score` 하나다.

| 소비처 | 영향 |
|---|---|
| BKT 관측 (`conceptJudgments`) | **없음.** 미답변 문항은 이미 태그 전부 `understood: false`로 고정 |
| 부제 "N개 중 M개 정답" | **없음.** `userReason`이 있는 문항만 센다 (그래서 모순이 눈에 보였다) |
| `isCorrectAnswer` / 화면 카드 | **없음.** 위 3분기에서 이미 확정 |
| `feedback.js` 승급 판정 | 있다 — 아래 |

`feedback.js`의 승급은 이해도(`evaluatePromotion`)로 하지만, **오개념 데이터가 없는 소단원**
(`result.total === 0`)에서는 폴백으로 `_legacyPromotionCheck(uid, session, isPassed)`가 돌고
`isPassed`는 `data.score >= PROMOTION_SCORE[level]`(L1·L2는 100)이다. 즉 부풀려진 100점이
**아무것도 안 쓴 학생을 승급시킬 수 있었다.** `_renderCorrectionLoop(isPassed)`도 합격으로 보고
"다시 풀어보기" 버튼을 숨긴다. 두 경우 모두 서버에서 점수를 바로잡는 것으로 함께 해결된다.

**로그로는 확인할 수 없었다.** `gradeAnswers`는 문항별 AI 점수를 어디에도 남기지 않고
(`console.*` 3줄은 상한 초과·라벨 불일치·개념별 판정뿐), 저장되는 `items`에도 `score` 필드가
없다. 실제 발생 여부를 사후에 셀 방법이 아예 없었다는 뜻이라, 위의 경고 로그를 같이 넣었다.
앞으로는 "미답변 문항 가점 차단 N건"으로 모델의 규칙 위반율이 관측된다.

**검증.** S-9와 같은 방식으로 SDK·`firebase-admin`을 바꿔치기하고 `gradeAnswers.run({data, auth})`을
직접 불러 6가지를 확인했다. 수정 전 코드에서 ①②가 각각 100점·50점으로 재현되는 것도 같이 봤다.

| 시나리오 | 수정 전 | 수정 후 |
|---|---|---|
| ① `answers: []` + 틀린 문장에 `score: 100` | 100점 | **0점** |
| ② 옳은 문장에만 답변 + 미답변 틀린 문장에 `score: 100` | 50점 | **0점** (가점 차단 + 헛다리 -50) |
| ③ [회귀] 틀린 문장에 답변 + `score: 100` | 100점 | 100점 |
| ④ [회귀] 틀린 문장에 답변 + 부분 점수 40 | 40점 | 40점 |
| ⑤ [회귀] 옳은 문장만 체크 (헛다리 감점) | 0점 | 0점 |
| ⑥ [오탐] 미답변 + AI도 0점 | 0점 | 0점, 경고 로그 없음 |

②가 실제로 마주칠 경로다. 프론트(`quiz.js`)는 **체크한 문장만** `answers`에 담고 최소 1개
서술을 요구하므로 UI에서 `answers: []`는 나오지 않는다. 하지만 체크하지 않은 틀린 문장은
`answers`에 없는 채로 채점 프롬프트의 전체 문장 목록에는 실려 AI가 점수를 매길 수 있다.
①은 함수를 직접 호출하면 가능하다.
